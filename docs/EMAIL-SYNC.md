# Синхронизация между устройствами

## Личный код: работает без писем

1. На устройстве с нужным прогрессом открыть сайт, нажать **Войти → По личному коду → Создать код и сохранить прогресс**.
2. Дождаться **Сохранено в облаке**, затем нажать **Скопировать код**. Сохранить его у себя.
3. На другом компьютере или телефоне открыть тот же сайт, нажать **Войти**, вставить код в поле **Личный код с первого устройства** и нажать **Подключить по коду**.

Дальше синхронизация автоматическая. Новый код создавать на втором устройстве не нужно: новый код создаёт отдельный профиль. При первом создании код забирает текущее гостевое прохождение; при подключении существующего кода гостевые результаты второго устройства добавляются отдельной кнопкой.

Код даёт полный доступ к этому учебному профилю. Не публиковать его и не отправлять посторонним. Его можно снова посмотреть в аккаунте подключённого устройства. При потере кода и выходе на всех устройствах восстановления по почте нет. Код не является паролем Supabase или Яндекса.

Вход по почте сохранён как отдельный способ, с отдельным профилем. Он не связывает почту с кодом автоматически.

## Вход по email

Адрес сайта: https://big-arch.github.io/Learn_Code/

1. Нажать **Войти**, ввести почту и открыть ссылку из письма.
2. В **Аккаунте** нажать **Перенести гостевой прогресс**, если до входа уже проходили задания в этом браузере.
3. На другом устройстве запросить письмо на тот же адрес. Прогресс загрузится после входа.

В обоих режимах переносятся завершённые уроки, задания, XP (без повторного начисления), черновики основного курса, Арены, острова, мастерской, практикумов Python и HTML/CSS, дополнительных видеопрактик, настройки звука и движения. Введённые временные input()-данные и открытая вкладка урока не синхронизируются.

Гостевой профиль отдельный. Он не перезаписывается аккаунтом при выходе и не импортируется в другой аккаунт автоматически. Перенос из гостя относится к текущему браузеру и адресу сайта: localhost и GitHub Pages имеют разные браузерные хранилища.

## Синхронизация

Изменения отправляются через 650 мс после редактирования. Восстановление сети, возвращение на вкладку и периодическая проверка раз в 30 секунд подтягивают облачные изменения. Кнопка «Синхронизировать» запускает проверку вручную. Офлайн-изменения хранятся под отдельным ключом аккаунта и повторно отправляются после восстановления связи.

Объединение выполняется относительно предыдущей синхронизированной версии. Достижения объединяются; XP пересчитывается по известным заданиям. Независимые черновики сохраняются вместе. При изменении одного черновика с двух устройств обе версии показываются в аккаунте для явного выбора. Во время незавершённого запроса новые локальные правки не теряются.

Сброс требует доступного облака. Он увеличивает поколение состояния: старая офлайн-копия не возвращает удалённые достижения. Предыдущая локальная копия остаётся доступна для скачивания в аккаунте.

## Подключение

По выбору владельца использован существующий проект **big-arch's Project**, ref `renbakjudvdnkjvjujti`. Созданы только объекты с префиксом `learn_code_`: таблица `learn_code_progress`, проверка состояния и RPC `learn_code_sync`. Схема — `server/learn-code-cloud.sql`, применена миграция `learn_code_email_progress`.

Вход — Supabase Auth Magic Link, клиентская SPA использует официальный SDK 2.119.0 и поддерживаемый implicit callback. Токены в URL обрабатывает SDK; приложение не пишет их в логи. Секретные/service-role ключи не используются. Публичный URL проекта и publishable key задаются переменными сборки `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY`; они доступны клиенту по назначению.

RLS ограничивает SELECT/INSERT/UPDATE условием `auth.uid() = user_id`. RPC работает как SECURITY INVOKER, требует вход и сам определяет user_id. Анонимный доступ к таблице и RPC отозван. Проверка revision и блокировка строки предотвращают потерю состояния при одновременной записи. Письма и Redirect URLs настраиваются в Supabase; владелец подтвердил настроенный SMTP и добавление адреса сайта в Redirect URLs.

Для локальной облачной сборки заполнить `.env.local` по `.env.example`; без переменных аккаунты скрыты, гостевой/SQLite режим работает как раньше. Для тестирования email-входа в локальную версию дополнительно требуется подходящий адрес возврата; опубликованная форма направляет письмо на рабочий сайт.

### Устройство режима по коду

`server/learn-code-device-sync.sql` добавляет закрытую таблицу `learn_code_private.device_progress` и RPC `learn_code_device_sync`. Существующие Auth и таблицы других приложений не изменяются. Код генерируется Web Crypto (160 случайных бит), отправляется только в теле HTTPS-запроса, хранится в базе как SHA-256. В браузере код сохраняется для повторного подключения; в URL, скриншоты QA, логи приложения и экспорт прогресса он не включается. Публичные ключи проекта не являются ключами доступа к профилю.

Это самостоятельная авторизация по секретному коду, не Supabase Auth. Проверка `auth.uid()` здесь не применяется: закрытая SECURITY DEFINER-функция проверяет хеш кода, а публичная обёртка работает как INVOKER. Пустой search_path, явные права EXECUTE; прямые SELECT/INSERT/UPDATE/DELETE для anon/authenticated запрещены, RLS включён без разрешающих политик. Информационное замечание advisors «RLS Enabled No Policy» для этой закрытой таблицы ожидаемо: прямой доступ намеренно запрещён ([описание](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy)).

Создание повторяется с тем же временно сохранённым кодом при потере ответа; повторный запрос не перезаписывает профиль. Запись проверяет revision и блокирует строку; reset меняет epoch. Новые профили ограничены 500 за скользящие 24 часа, существующие продолжат синхронизацию. JSON ограничен существующим валидатором Learn Code. Секретные ключи администратора клиенту не выдаются.

Реальный PostgreSQL дополнительно проверен в транзакции с откатом: два независимых кода, CAS, повторное создание, сброс, запрет прямого доступа, неверный код и невалидное состояние. Источники: [Supabase Database Functions](https://supabase.com/docs/guides/database/functions), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security).

### Что мешает email-входу

Последняя прочитанная ошибка SMTP от 9 ноября 2026 22:55 UTC (10 ноября 01:55 МСК): 535 Invalid user or password. Яндекс отвергает авторизацию отправителя. Название BookWords в поле Sender name — подпись отправителя, не ограничение количества приложений.

Проверить разрешение почтовых клиентов IMAP и «Пароли приложений и OAuth-токены» в Яндекс Почте, затем создать пароль приложения **Почта** для отправителя `big-arch@yandex.ru` и сохранить его в SMTP Supabase. Host `smtp.yandex.ru`, порт 465, Username — полный адрес отправителя. Пароль в чат не пересылать. [Официальная инструкция Яндекса](https://yandex.ru/support/yandex-360/customers/mail/ru/mail-clients/others), [разбор ошибок авторизации](https://yandex.ru/support/yandex-360/customers/mail/ru/mail-clients/mail-clients-troubleshooting).
